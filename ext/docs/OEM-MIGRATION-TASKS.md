# OEM 功能移植到新系统：实施任务与验收（v0.5，2026-11-13）

依据：`AGENTS.md`（宪法 v0.5）、`SOLUTION.md`（方案 v0.5）。本文件只覆盖 OEM（品牌站）这一条线，其余模块另立文件。**新系统不迁移旧系统数据；本文件是"把 OEM 的业务能力在新系统里重建"，不是"把旧 OEM 搬过去"。**
任务按阶段编号 `T<阶段>.<序号>`；每个任务给出产出物与验收标准。验收标准是"可观察、可复核"的结果，不写"完成开发"这类无法核对的话。

---

## 0. 旧系统 OEM 的真实构成（移植参照盘点）

盘点时间 2026-11-12，来源：当前仓库 `main`（19.541）只读统计。

| 层 | 规模 | 说明 |
|---|---|---|
| 数据表 | **56 张** `Brand*` 表 | 站点、客户、团队、代理商、钱包、信控、订单、退款、结算单、对账、通知、审计等 |
| 后端代码 | **108 个文件，约 22,000 行**（model 61、controller 31、service 13、middleware 1、router 2） | 不含测试 |
| 对外接口 | `/api/brand/*` 共 **197 条路由**：public 15、customer 25、team 102、manage 约 55 | manage 为品牌主控制台，team 为团队/代理商后台 |
| 租户边界 | `middleware/brand.go` 按 Host 识别品牌，路径白名单放行 | 这是最关键的隔离点 |
| 静态前端 | `brandweb/`：品牌站模板 + 经营/企业/工单脚本 + 用量日志子应用 + 商家手册 | Go 模板渲染，独立于主站前端 |
| 主站后台页 | 品牌管理 `/brand-console`、OEM 统计、OEM 客户与额度等 | 在主站前端里 |
| 文档链路 | 主站文档 → `tools/sync-oem-docs.mjs` → `brandweb/docs.json`；商家手册 `docs/oem-merchant-guide.json` → `sync-merchant-guide.mjs` | 构建时校验同步 |
| 后台任务 | 域名验证/证书、统一钱包自动化、支付宝自动化 | `main.go` 启动 |
| 构建开关 | `CMH_BUILD_BRAND_WALLET_NEW/COMPAT`、`BRAND_MERCHANT_ALIPAY_*`、`BRAND_PLATFORM_VOUCHER_NEW` | 资金功能的编译期门禁 |
| 侵入官方核心的点 | `auth.go` 18 处、`relay_task.go` 15 处、`web-router.go` 11 处、`billing.go` 10 处、`relay.go` 8 处、`price.go` 7 处、`task_polling.go` 5 处、`main.go` 4 处 | **这些是新仓库里必须收敛到挂载点的部分** |

结论：OEM 是扩展区里最大、资金风险最高的模块。在新系统里按宪法分层**重建**，业务规则以旧系统的规则文档（`docs/brand-sites.md`、`PROJECT_RULES.md` OEM 各条、`PROMOTION_COMMISSION_BIBLE.md`）为依据并记录版本；数据结构可以重新设计，不受旧 56 张表约束。

## 1. 阶段划分与依赖

```
T0 基座 → T1 骨架与挂载点 → T2 租户与品牌站只读 → T3 品牌资金链 → T4 团队/代理商/收款/文档 → T5 上线
```

- T0、T1 是全仓库的前置，不只服务 OEM；本文件列出的是 OEM 需要它们提供的部分。
- T2 之前 OEM 不碰资金；T3 开始才进入资金链，必须完成 T1 的 H3/H4 挂载点验收。
- 每个阶段结束都要执行一次"同步官方"演练（宪法 §7），作为该阶段的最后一条验收。

## 3. 跨阶段的固定验收项（每阶段结束都做）

| 编号 | 检查 | 通过标准 |
|---|---|---|
| G1 | 官方区 diff | `git diff upstream/<基线> -- <官方区>` 命中文件 ⊆ `ext/docs/HOOKS.md`；总行数 ≤ 150（硬上限），目标 ≤ 80 |
| G2 | 依赖方向 | 官方区无 `import ".../ext/"`（静态扫描） |
| G3 | 表名 | 扩展区新表全部 `cmh_` 前缀 |
| G4 | 同步演练 | `merge upstream/main` 冲突只在挂载点文件 |
| G5 | 品牌隔离 | 品牌页/文档/错误信息不含平台主体、平台域名、上游名称（禁词测试） |
| G6 | 资金守恒（T3 起） | 守恒测试全绿（含 `BATCH_UPDATE_ENABLED` 开/关）；对账零差异 |
| G7 | 文档同步 | 主站文档与 OEM 生成物一致；商家手册版本与功能版本一致 |
| G8 | 三库验证（涉及表时） | SQLite / MySQL / PostgreSQL 各跑一遍迁移与核心用例 |
| G9 | 官方计费规则（涉及计费时） | 对照 `.agents/rules/billing.md`：多重因子有上界、量化走 `quota_math`、无裸 `int()` |

## 4. 风险与应对

| 风险 | 应对 |
|---|---|
| 挂载点不够用，开发中想直接改官方文件 | 走宪法 §3.4 RFC；CI 不放行越界改动 |
| H3 接口携带的信息不够品牌计费用 | 在 T1.5 就用旧系统的品牌计费字段清单（R/P/C/版本/来源/渠道/用量）反推接口结构，一次定全 |
| 接管型漏掉某个资金出口，官方与 ext 重复扣款 | T1.6c 的全仓调用点清单是硬性产出；新增任何调用 `DecreaseUserQuota` 系列的官方代码，在同步演练时必须重新核对（纳入 G4） |
| 资金语义在重建中走样 | T3 以当前仓库的规则文档（`docs/brand-sites.md`、`PROJECT_RULES.md` OEM 各条）为验收依据，逐条映射成测试用例 |
| 前端注入方式官方后续变更 | T0.2 的注入方式写入文档并加回归测试；同步官方时纳入 G4 检查 |
| 新系统初期无真实品牌流量，资金链问题发现晚 | T5.3 尽早开通第一个真实品牌；T3 的守恒测试覆盖未知结果、超时免单、退款等全部分支 |
| 两套系统规则逐渐不一致，运营口径混乱 | 移植时记录依据的旧系统版本；之后新系统独立迭代，不强求一致 |
