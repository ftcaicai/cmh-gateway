# RFC（设计复核，未批准）：资金接入保持同事务，不实施四入口提前返回

## 决策边界

用户明确选择“同事务”。本RFC不擅自将它替换成“官方扣款一次、OEM最终一致一次”或“只跳过官方钱包”。原先 `handled` 在整个BillingSession入口直接return的计划已被源码复核否定，详见 `../acceptance/p1/funding-lifecycle-audit.md`。

## 必须先通过的技术问题

1. 定义财务事务集合：请求受理记录、价格版本快照、资金来源预留、客户/OEM/代理资金本体、资金事件、outbox是否在同一事务。token限额不能默认独立；若与资金一起要求原子，必须有显式tx-aware更新并在提交后修缓存。
2. 明确资金所有权：官方钱包承担主站账号资金，品牌钱包如何关联官方用户/Key；不可临时造余额、设无限额Key或在缓存里屏蔽检查。
3. 预扣/追加预留/回滚/结算/退款/违规费用各有事件身份。基础退款与违规补扣不能共用一个幂等键。
4. 请求与异步任务保存不可变租户/资金归属。后台无Host，无Gin context；任务终态不是财务终态，财务失败必须可重新扫描，而不是因任务已SUCCESS从轮询队列消失。

## 推荐探索路径（不是已通过设计）

以官方 `FundingSource` 为资金来源抽象基础，增加启动期工厂/适配桥：在官方钱包/订阅准入检查前选择extension资金来源，保留官方BillingSession锁、token状态、信任检查语义和错误映射。

但当前接口 Source/PreConsume/Settle/Refund 还不够：reserveFunding/rollback、NeedsRefund、syncRelayInfo依赖具体WalletFunding/SubscriptionFunding类型；task和direct PostConsumeQuota/MJ也没有复用同一对象。需要先做隔离原型完整生命周期清单，不能写一个实现类就宣布接入。

### 同事务实现候选

- 扩展适配器在短主库事务内调各模块公开的tx-aware操作，锁顺序固定，幂等事件唯一约束和余额变更同提交。
- 涉及官方表时不能把调用全局DB的model方法包在ext事务外壳内冒充同事务。需要明确的tx-aware官方桥接，属于需批准的最小补丁。
- Redis、批量队列不作为财务事实；已接管请求的金融写入不能延迟到内存队列。缓存失效/派生日志在提交后outbox恢复。
- 函数若不能安全纳入，不在品牌域开放该协议（特别是Realtime、MJ、订阅），并返回明确不支持；不静默回退官方钱包。这不是授权删功能，协议范围须形成能力矩阵。

## 原型退出标准

- 同一请求各资金阶段追踪图与所有写入口清单（含raw SQL、Save、支付与管理员入款）。
- 业务值守恒按账户分类定义：可用/预留是同一资产的状态，不可与平台已收/应收无符号相加而双计。账本每个事件借贷和为零；余额=期初+已提交有符号事件；请求预留净额=预留+追加-消费释放-退款释放，终态为零（明确欠款/人工待核例外单列）。原方案的简单四项之和公式不能当会计验收。
- 真实SQLite/MySQL/PostgreSQL新库/升级/重复启动、并发、Redis×BATCH、进程重启与故障注入。
- token扣款失败、资金已提交但task marker失败、退款异步失败、迟到任务与订阅周期重置等各有确定期望。
- 产出真实官方diff和持续同步成本，预算仍为150行/10文件；不能为过预算压缩代码、漏路径或删除校验。

## 当前实施约束

不改官方资金逻辑，不写钱表，不开放品牌财务请求。先以纯值类型和合成用例验证契约，发现规则/预算不够时明确向用户请求决策。此RFC不是对新架构或预算扩大的批准。
