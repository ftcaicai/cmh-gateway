# AGENTS.md — 新仓库协作宪法（草案 v0.6，2026-11-13）

本文件是以官方 new-api 为基座、长期跟随官方更新的新仓库的根规则，存放于 `ext/AGENTS.md`（根目录 `AGENTS.md` 是官方的，只读）。所有人和所有 AI 助手在本仓库工作前必须先读本文件。本文件与官方 `AGENTS.md` 同时生效；两者冲突时，关于目录边界和同步的规则以本文件为准，关于代码风格以官方为准。

仓库来源：GitHub fork 自 `QuantumNous/new-api`，基线为官方 release tag（首个基线记录在 `ext/docs/sync-log.md` 第一行）。许可证 AGPL-3.0，对外提供服务时须向用户提供对应源码并保留官方署名与原项目链接。

本文件只定规则和目录，不定实施计划。实施计划另立文档。

---

## 0. 一句话原则

**官方代码只读；我们的一切放在它旁边；两者只通过登记在册的挂载点相连。**

所有规则都是这句话的展开。判断任何做法是否允许，先问：这会不会让下一次同步官方变难？会，就不做。

│
├── plugins/tasks/                 官方插件目录
│   ├── <官方自带插件>/             官方区，只读
│   └── cmh-*/                     我们的插件，目录名必须以 cmh- 开头，见 §4；只放 plugin.js、icon、fixture
│
├── web/                           官方前端，官方区，只读
├── web-cmh/                       我们的独立前端应用（不注入官方前端），见 §6
├── brandweb/                      OEM 品牌静态站（Go 模板，由 ext/brand 渲染）
├── ops/                           构建、发布、运维、CI 检查脚本
└── AGENTS.md                      官方的，只读；我们的宪法在 ext/AGENTS.md

### 1.1 三个区的定义

| 区 | 范围 | 谁能改 |
|---|---|---|
| **官方区** | 官方仓库里存在的所有路径，包括 `web/`、`docs/`、`plugins/tasks/<官方插件>/`、`relay/`、`model/` 等 | 只有挂载点补丁可以改，见 §3 |
| **扩展区** | `ext/`（含本文件 `ext/AGENTS.md`）、`plugins/tasks/cmh-*/`、`web-cmh/`、`brandweb/`、`ops/` | 我们自由修改 |
| **挂载点** | 官方区中登记在 `ext/docs/HOOKS.md` 的少数文件 | 按 §3 流程改 |

判断一个路径属于哪个区：`git diff --name-only upstream/main` 里出现的官方路径就是官方区。新建的路径若不在扩展区名单内，默认视为官方区，禁止创建。

## 2. 官方区规则

- **2.1 只读。** 不新建、不修改、不删除官方区文件，不重命名官方区目录。唯一例外是 §3 的挂载点补丁。
- **2.2 不 import 扩展区。** 官方区代码不得 import `ext/` 或任何我们的包。依赖方向只允许 `ext → 官方`，永远不允许反向。挂载点靠接口变量解耦，不靠 import。
- **2.3 不改官方表结构。** 不给官方的表加列、改列、加索引。需要关联官方数据时，在扩展区建自己的表，以外键或 ID 引用。
- **2.4 不改官方常量和编号。** 不新增渠道类型编号、不修改 `constant/` 下的枚举。新上游一律走插件（§4）。
- **2.5 不改官方前端。** 页面、组件、路由、i18n 文件都不改。我们的页面放 `web-cmh/`。
- **2.6 不绕过官方的验证和计费。** 不在扩展区复制一份官方逻辑再改，而是通过挂载点在官方流程里插入逻辑。
- **2.7 CI 强制。** CI 对每个 PR 执行"官方区 diff 检查"：`git diff upstream/<基线> -- <官方区路径>` 的结果，只允许命中 `ext/docs/HOOKS.md` 登记的文件。命中未登记文件，CI 失败，不接受人工放行。
- **2.8 遵守官方自身规则。** 官方 `AGENTS.md` 与 `.agents/rules/billing.md` 对扩展区同样生效：触碰计费先完整读 billing.md；鉴权改动符合 OWASP ASVS 并记录验证；涉及表的改动在 SQLite/MySQL/PostgreSQL 三库实测。根 `docs/` 与 `plugins/tasks/<plugin>/` 内不新增文档是我们为保持同步干净而**主动选择**的约束，不因官方规则留有例外而放松。

## 3. 挂载点规则

挂载点是官方区里**唯一允许被我们修改的位置**。形式固定：`ext/core` 定义接口类型和包级变量，官方代码里只加一处调用；默认实现为空操作；扩展区在启动时替换这个变量。

挂载点分两种形态：
- **观察型**：不改变官方控制流，官方调用后继续原逻辑。
- **接管型**：接口返回 `handled bool`；为 `true` 时官方跳过自己的那一步，由扩展区完成。只用于资金出口（H3、H7），因为官方的预扣/结算没有事务可供加入，品牌客户的资金必须由扩展区完整接管才能守恒。

### 3.1 挂载点清单（初始）

| 编号 | 名称 | 形态 | 官方位置（已对照官方 main 核对） | 注入内容 |
|---|---|---|---|---|
| H1 | `ModelGate` | 观察 | `middleware/distributor.go` 选渠道前；`controller/channel.go` `AddChannel`/`UpdateChannel`；`model/pricing.go` `updatePricing()` | 国产白名单、渠道类型白名单、上架门禁 |
| H2 | `TenantResolver` | 观察 | `main.go` 中间件链，`RequestId()` 之后 | 按 Host 识别 OEM 品牌写入 context、品牌域路径白名单 |
| H3 | `FundingHooks` | **接管** | `service/billing_session.go` `preConsume` / `Settle` / `Refund` | 品牌客户的预扣、结算、退款由扩展区在自己事务内完成；派生的返佣、发票额度、利润快照随后写入 |
| H4 | `PricingResolver` | 观察 | `relay/helper/price.go` `ModelPriceHelper` / `ModelPriceHelperPerCall` 返回前 | 分组+模型售价版本、客户专属价、OEM 结算价 |
| H5 | `RouteRegistrar` | 观察 | `router/main.go` `SetWebRouter` 之前 | `ext.Register(router)`：品牌 API、扩展 API、品牌静态站、`/cmh/*` 静态资源 |
| H6 | `Migrator` | 观察 | `model/main.go` `migrateDB()` 末尾 | `cmh_*` 表 |
| H7 | `TaskFundingHooks` | **接管** | `service/task_billing.go` `taskAdjustFunding` | 任务结算/退款的品牌资金接管 |

精确行号在实施时写入 `ext/docs/HOOKS.md`。

### 3.2 数量上限

挂载点总数**不超过 10 个**，涉及官方文件**不超过 10 个**，官方区总 diff **不超过 150 行**（设计目标 ≤ 80 行）。接近上限时必须先合并或精简已有挂载点，不得突破。

### 3.3 每个挂载点的要求

- 一个挂载点一个 commit，commit 标题固定为 `hook(Hn): <名称>`。
- 挂载点接口定义放在 `ext/core/`，官方区只写一处调用，不写逻辑。
- 观察型默认实现必须是空操作；接管型默认实现必须返回 `handled=false`。两者都保证去掉 `ext/` 后官方代码仍可编译、行为与官方完全一致。
- 接管型只允许在函数入口以 `if handled { return }` 形式出现，不得改写函数体。
- 接管型的 `handled` 判断只读请求上下文，不查数据库。
- `ext/docs/HOOKS.md` 登记：编号、名称、形态、官方文件路径、行号范围、加入日期、用途、负责人。代码变了登记表必须同步变。

### 3.4 新增或修改挂载点的流程

1. 先证明三种非侵入方式（§4 插件、`ext/` 独立实现、现有挂载点）都做不到，写成 `ext/docs/rfc/<日期>-<名称>.md`。
2. RFC 说明：要解决的问题、为什么非侵入做不到、改哪个官方文件、改多少行、对同步的影响。
3. RFC 经负责人确认后才能动官方代码。
4. 完成后更新 `ext/docs/HOOKS.md`，并在下一次同步官方时专门验证该挂载点。

## 4. 插件规则

所有新上游渠道、所有对请求/响应的改写，一律先用官方插件机制实现。

- **4.1 一个上游一个插件目录**，目录名以 `cmh-` 开头，放在 `plugins/tasks/`。
- **4.2 不占渠道类型编号。** 插件走官方 Task Plugin 渠道类型（type 61），不新增类型。
- **4.3 插件只管协议。** 提交、轮询、参数映射、响应转换、计费单位声明放在插件里。官方沙箱没有 fetch、文件、异步、eval，也不能算价和结算；需要数据库、持久状态、跨请求事务的逻辑（素材库、回跳、幂等记录等）放在 `ext/` 对应模块，插件只报用量事实。
- **4.4 对客不暴露上游。** 插件的对客模型名、错误信息、响应字段一律使用本站公开名称，不出现上游供应商名、上游模型 ID、上游地址。
- **4.5 每个插件自带 fixture。** 目录内必须有 `golden.json`，用官方 `new-api plugin test` 可跑通；插件说明写在 `ext/docs/plugins/<key>.md`，**不在插件目录放 README**（官方禁止）。
- **4.6 插件失败不能影响官方区。** 插件加载失败、运行异常只影响该插件对应渠道，不得导致进程退出或其他渠道不可用。
- **4.7 计费字段遵守官方约定。** `usageSchema` 数值字段的 `description` 写"计费对象 + 单价"，单位放 `unit`；用量多重因子在插件内先有上界。

## 5. 扩展区内部规则

- **5.1 模块隔离。** `ext/` 下各模块只通过接口互相依赖，禁止直接读写其他模块的表。需要共享的数据结构放 `ext/core/`。
- **5.2 表名前缀。** 扩展区所有表名以 `cmh_` 开头，避免与官方现有或未来新表撞名。
- **5.3 独立迁移。** 扩展区的表由 `ext/migrations/` 管理，与官方 AutoMigrate 分开；只允许加表、加列，不允许改列、删列。
- **5.4 路由前缀。** 扩展区对外接口统一在 `/api/ext/` 或各模块固定前缀下，不与官方路由重叠；品牌站、OEM 等已有对客路径按业务需要保留，但须在 `ext/register.go` 集中登记。
- **5.5 不依赖官方内部细节。** 只调用官方导出的、稳定的函数和类型。官方未导出的、带 `internal` 的、注释标明不稳定的，一律不用。用了官方内部细节的代码，在同步官方时视为我们的责任。
- **5.6 资金与权限代码的额外要求。** 钱包、结算、退款、权限相关改动必须有事务、幂等、守恒测试；守恒测试必须覆盖 `BATCH_UPDATE_ENABLED` 开与关两种模式；必须由**未参与该改动开发**的人独立复核并在验收记录签字。此条不因重构而放松。
- **5.7 复用官方基础设施。** 权限用官方 Casbin（`service/authz`）定义策略，不自建角色表；配置热更新用 `service.RegisterSyncTopic`；定时任务注册为官方系统任务，不自起 goroutine 轮询。
- **5.8 量化与上界。** 扩展区所有金额/用量转换走官方 `common/quota_math.go`，不得手写 `int()` 转换；用户可控的计费乘数在进入计算前必须有上界。

## 6. 前端规则

- **6.1** 官方 `web/` 只读，构建产物直接使用官方构建链。官方前端用文件路由自动生成路由树，没有外部注入口，因此不向 `web/src/routes/` 加任何文件。
- **6.2** 我们的页面是独立应用 `web-cmh/`，自带构建配置，产物由 `ext` 在 `/cmh/*` 下提供；与官方同栈（React 19 + TanStack + Rsbuild）以便复用组件。
- **6.3** 官方前端没有自定义导航入口（`HeaderNavModules` 只开关固定模块，前端不渲染未知键）。`web-cmh/` 自带完整导航，`/cmh/` 是运营与品牌主的直达入口；不改官方导航组件。要在官方界面放链接，走 §3.4 RFC。
- **6.4** 复用官方 `web/src/components/` 导出的组件，不复制改造；国际化文案放 `web-cmh/` 自己的翻译文件。
- **6.5** `brandweb/` 保持 Go 模板静态站，由 `ext/brand` 渲染，不与任何 React 前端耦合。
- **6.6** 对客文档（站内文档、OEM 文档、OpenAPI）与接口行为同次变更、同次发布，沿用现有"文档同步"永久规则。

## 7. 同步官方规则

- **7.1 分支。** `upstream/main` 只读；`main` 为发布线；`develop` 为开发线；每次同步开临时分支 `sync/<YYYYMMDD>`。**不使用 GitHub 的 "Sync fork" 按钮**，它会绕过 §7.3 流程直接合并。
- **7.2 节奏。** 以官方 **release tag** 为同步单位（不是 `upstream/main` 的任意提交），每个 release 跟一次，不攒。超过一个 release 未同步，需要在周会说明原因。
- **7.3 流程。**
  1. `git fetch upstream --tags`，开 `sync/<日期>`，`merge <官方 release tag>`。
  2. 冲突只应出现在 `ext/docs/HOOKS.md` 登记的文件。出现在别处，说明有越界改动，先修越界，再继续同步。
  3. 跑官方全量测试 + 扩展区全量测试 + 插件 fixture 测试。
  4. 逐个验证 §3.1 的挂载点仍然生效。
  5. 合入 `develop`，走正常发布。
- **7.4 同步记录。** 每次同步在 `ext/docs/sync-log.md` 追加一行：日期、官方版本、冲突文件、处理方式、验证结果。
- **7.5 同步不等于发布。** 同步后的版本仍须走完本仓库发布门禁。

### 7.6 与旧系统的关系（2026-11-13 负责人决定）

- 本仓库是**全新系统**，不替换旧系统；旧系统独立运行，两者不共享数据库、域名、客户和渠道配置。
- **不迁移旧系统任何数据**，不做新旧系统之间的对账、同步或互通。
- 旧系统的有用功能由负责人**逐项下指令**移植到本仓库；移植的是业务规则和能力，不是数据。指令须指明功能范围与依据的旧系统版本。
- 移植时以旧系统当时的规则文档为依据并记录版本；移植后本仓库独立迭代，不强求与旧系统保持一致。
- 后续产品迭代以本仓库为主。
- 每项移植在 `ext/docs/transfer-log.md` 登记：功能、范围、依据的旧系统版本、完成日期、验收证据路径。

## 8. 发布与运维规则

- **8.1** 构建脚本在 `ops/`，构建时注入白名单等 ldflags，并用探针校验二进制内容与预期一致。
- **8.2** 保留现有发布门禁：备份、发布锁、蓝绿切换、自然排空、同制品验收、回滚目标明确。
- **8.3** 不在生产直接改数据、改配置绕过流程。维护操作走 `ext/maintenance` 控制面。
- **8.4** 密钥、凭据、客户数据不进仓库、不进文档、不进聊天记录。

---

## 9. 禁止事项（直接判定违规）

1. 修改官方区任何未登记的文件。
2. 新增渠道类型编号。
3. 官方区 import 扩展区。
4. 给官方表加列或改列。
5. 复制官方逻辑到扩展区再修改。
6. 在扩展区使用官方未导出或标注不稳定的内部细节。
7. 以"紧急"为由跳过 RFC 直接改官方代码。
8. 同步官方时手工放行官方区未登记文件的冲突。
9. 扩展区模块直接读写其他模块的表。
10. 在插件、文档、错误信息中暴露上游名称、地址、模型 ID。
11. 向根 `docs/`、`plugins/tasks/<plugin>/` 或 `web/src/routes/` 新增文件。
12. 触碰计费却未读官方 `.agents/rules/billing.md`，或在扩展区手写量化转换。
